## Dashboard behavior

The Visit history section uses the selected 1/7/30/90/180-day date range:

- **Daily location history** shows each date, city, region, country and total
  page views, including previously stored daily records. Multiple pages from
  the same location on the same UTC date are combined.
- **Individual page views** shows each newly recorded page view's server date
  and time, city, region and country. Times are UTC. It cannot reconstruct
  individual times from the earlier daily aggregates.
- Search by city or region. Searches apply to the database, not only to the
  current page. Results appear newest first; Load more retrieves earlier rows
  in pages of 50, without the top-100-location limit of the overview table.

A page view is not a unique visitor or a session. Repeated views do not identify
a returning person. VPNs, mobile networks and privacy tools still affect
location estimates and collection.

## Storage and privacy

Migration `0002_visit_events.sql` adds a separate event table containing an
internal event row number, server timestamp, approved page path, country,
region and city. The row number identifies a page view, not a person. The
existing `location_counts` table is retained without backfilling fake events.

No raw IP address, visitor identifier, cookie, user-agent, precise coordinates,
query string or URL fragment is stored. Both tables retain 180 UTC dates; the
existing daily retention task deletes older rows. Exact timestamps are newly
stored for individual page views. Tracking writes the aggregate and event in
one database transaction so failures cannot update only one of them.

The new `/api/history` endpoint requires the same dashboard access key as
`/api/stats`. It uses bound SQL parameters, bounded result pages, private
no-store responses and no CORS access. No credentials are added to the browser
tracking script or source repository. Worker observability remains disabled.
